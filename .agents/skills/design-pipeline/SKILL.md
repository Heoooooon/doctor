# 디자인 파이프라인

정보를 정확하게 배치하는 것과 팔 수 있을 만큼 완성도 있는 디자인은 다르다. 코드가 정상이고 레이아웃이 안 깨져도 사진, 타이포, 밀도, 카피가 설득하지 못하면 완료가 아니다. 이 스킬은 절차이며 과거 승인이나 현재 PASS의 증거가 아니다.

## 사용 범위와 읽을 자료

- 설명·조사 요청이면 근거와 판단만 보고한다. 리뷰·개선 제안이면 평가 후 확인을 기다린다. 명시적인 제작·수정 요청만 해당 범위의 구현을 허용한다. 스킬 호출이 배포·커밋·병합 권한을 만들지 않는다.
- 먼저 대상 저장소의 `AGENTS.md`, `docs/brand.md`, `docs/design-system.md`, `docs/seo-guide.md`, `docs/medical-law.md`를 읽는다. 다른 프로젝트에서는 대응 문서와 경로를 기록한다. 환자용 치과 사이트와 B2B 솔루션 소개의 대상·사업 신원을 혼동하지 않는다.
- 기존 `design/taste-profile.md`, `design/DIRECTION.md`, `design/concepts/REVIEW.md`, `DESIGN.md`, `research/exposure-strategy/README.md`가 있으면 먼저 재사용한다. 다른 worktree에 있으면 위치·버전·적용 범위를 인계 기록에 연결한다. 완료된 대규모 연구를 재실행하지 말고 필요한 누락·변경 사실만 보완한다.
- [평가 루브릭](references/rubric.md), [영문 위임 프롬프트](references/prompts.md), [실행·인계 체크리스트](references/checklist.md)를 함께 사용한다. 이 링크는 스킬 폴더 기준이다. 위의 코드 경로는 대상 저장소 기준의 입력 예시이며 스킬 내부 링크가 아니다.

서울이건치과에서는 Pretendard, 정보 우선, 실제 사진, 차분한 설명, 자연치아 보존을 기준으로 삼는다. 홈페이지 글자 크기 하한과 명시된 푸터 예외는 현재 디자인 시스템에서 확인한다. 브랜드와 디자인 시스템의 accent 값, SEO 예문의 전문의 표기, 후기·전후사진 조건처럼 문서가 충돌하면 복사로 해결하지 않는다. 토큰은 디자인 단일 소스와 실제 CSS를 대조하고, 자격·의료광고·개인정보는 검증된 사실과 더 엄격한 제한을 적용해 쟁점을 기록한다. 내부 가이드를 읽은 것이 법률 검토 완료는 아니다.

## 책임과 작업 경계

- 오케스트레이터가 범위, 근거 장부, 승인 상태, 브라우저와 최종 통합을 소유한다. 시작 시 `git status --short`, `git diff --stat`, `git worktree list`로 기준 상태를 기록하고 담당별 허용 파일·worktree·출력만 지정한다. 사용자 변경을 덮거나 reset/clean/stash로 치우지 않는다. 범위 밖 변경은 소유자에게 돌린다.
- Aside 브라우저 드라이버는 오케스트레이터 한 명뿐이다. 리뷰어·구현자는 브라우저를 병렬 조작하지 않는다. 개인 프로필의 쿠키·세션·스토리지 초기화 금지. 상태 실험은 승인된 격리 프로필·로컬 데모에서만 한다. 운영 예약 제출·외부 전송·배포는 별도 권한이 필요하다.
- 브라우저 조작 능력과 이미지 판독 능력은 별개다. 오케스트레이터가 픽셀을 읽을 수 없으면 그렇게 밝히고 이미지 판독 가능한 리뷰어에게 원본을 전달한다. 리뷰어의 구체적인 관찰을 출처와 함께 인용한다. DOM 치수·스크린샷 생성·OCR만으로 직접 픽셀 검수했다고 말하지 않는다.
- 템플릿에는 로컬 런타임 설치 경로, 현재 SHA, 개인 연락처, 비밀값을 고정하지 않는다. 실제 실행 기록에는 대상 버전·명령·증거 경로를 채우되 공유 자료는 비식별화한다. 연락처·사업 정보·의료진 자격은 발명하거나 고객 병원의 값을 B2B 사업자 값으로 전용하지 않는다.

## 절차와 게이트

### 1. 근거 기반 취향 정리

`design/taste-profile.md`에 선호·비선호, 직접 인용 또는 요약, 출처 파일/구간, 적용 해석, 불확실성, 금지 조건을 기록한다. 전언을 소유자 취향으로, 방문자 수치나 검색 추정을 사실로 바꾸지 않는다. 대상 독자·첫 질문·다음 행동과 모든 섹션의 목적을 정한다. 기존 결정은 새 요구·반증·자료 변경이 없으면 다시 열지 않는다.

### 2. 레퍼런스 수집

`design/references/README.md`에 출처 URL, 확인일, 캡처 경로·viewport, 가져올 원리/가져오지 않을 요소, 자산 권리를 적는다. 실제 열람과 세션 인용·과거 캡처를 구분한다. 실사진 또는 실제 제품 화면을 정보의 근거로 쓰며 무관한 분위기 사진, 무단 복제, 환자 사진 보정·합성을 피한다. 기존 연구·레퍼런스로 충분하면 수집을 끝낸다.

### 3. 읽을 수 있는 3방향 섹션 시안

같은 정보·안전한 실제 카피로 A/B/C 세 방향을 만든다. 색만 바꾼 변형 대신 정보 순서, 사진 비중, 타이포 위계·밀도 차이를 보여준다. `design/concepts/{A,B,C}/section-<id>-<viewport>.png`와 제작 원본, `design/concepts/MANIFEST.md`에 방향별 전체 섹션 목록·헤더/푸터·상태 계획을 연결한다. 연락처 등 미확정 값은 정직하게 표시한다.

전체 보드와 확대 가능한 개별 섹션을 모두 제공하고 최소 모바일·데스크톱에서 실제 카피가 읽히는지 확인한다. 긴 축소 이미지 한 장이나 고정 높이의 잘린 보드만으로 심사하지 않는다. 원본 픽셀 크기, CSS viewport, DPR을 구분한다.

이미지 생성 도구를 썼다면 모델/요청·결과 파일·성공/실패를 기록한다. 403이면 `이미지 생성 실패(403), 모델 생성 이미지 없음`으로 남긴다. HTML/CSS로 만든 대체 시안은 `HTML 렌더 시안`이며 생성 모델 이미지가 아니다. 파일명·캡션·보고서 어디에서도 이를 이미지 생성 성공으로 위장하지 않는다. 대체물의 승인 범위를 기록하고, 모델 이미지 자체가 필수 납품이면 그 항목은 미완료로 둔다.

### 4. 독립 이미지 리뷰 2명

서로의 답변과 오케스트레이터의 선호를 보지 않는 이미지 판독 가능한 리뷰어 두 명에게 같은 원본 묶음과 [루브릭](references/rubric.md)을 제공한다. 먼저 실제 열람 성공/실패 목록을 받는다. A/B/C의 **각 섹션**을 6축 1~5점으로 채점하고 정확한 이미지·위치·문제·수정안을 요구한다. 원문은 `design/reviews/concepts-r1.md`, `concepts-r2.md`로 보존하고 `design/concepts/REVIEW.md`에는 불일치와 비교를 종합한다.

구현 후보는 두 리뷰어가 각각 모든 섹션 평균 4/5 이상이고 미해결 잘림·CJK 줄바꿈·접근성·차단 결함이 없어야 한다. 전체 평균이나 두 사람 점수의 평균으로 실패 섹션을 숨기지 않는다. 탈락 방향은 비교 기록으로 남겨도 되지만 선택 후보는 수정·재심한다. 섞은 방향의 새 구성도 해당 섹션 재심 없이 이전 점수를 승계하지 않는다.

### 5. 소유자 방향 승인 체크포인트

`design/DIRECTION.md`에 추천 1개, 근거, 대안과의 차이, 차용 범위, 수정 사항, 두 리뷰 결과, 승인 요청 범위를 적는다. `추천`, `소유자 선택`, `가역적 구현 허용`, `최종 브랜드 승인`은 다른 상태다. 승인 주체·실제 지시 출처·범위가 없으면 `승인 대기`이며 UI 구현을 시작하지 않는다. 소유자가 추천안으로 계속 진행하도록 명시했다면 그 지시가 허용한 범위만 기록한다. 방향 승인도 품질 게이트 면제는 아니다.

### 6. DESIGN 계약

승인 범위를 `DESIGN.md`로 고정한다. 각 섹션의 목적·실제 카피·DOM 순서·기하·읽는 폭, 의미 토큰/서체/간격/표면, 자산 원본·치수·비율·권리, 반응형 규칙, 컴포넌트 상태·키보드·대비·모션, CTA의 실제 목적지, 오류/누락 상태, 시안과 의도적 차이, 완료 증거와 공개 의존성을 명시한다. 없는 자산은 슬롯이지 완료물이 아니다. 프로젝트별 승인 없이 과거 사이트의 섹션 수·팔레트·폰트 예외를 고정하지 않는다.

### 7. 실제 DOM으로 image-to-code

승인 이미지의 정렬·폭·크롭·타입·밀도를 추출하고 계약에 따라 시맨틱 HTML, 실제 텍스트·링크·컨트롤로 구현한다. 페이지 전체를 이미지로 덮거나 작동하지 않는 CTA로 흉내 내지 않는다. 제품 스크린샷 속 UI는 정적 예시임을 밝히고 핵심 설명은 DOM에도 둔다. 변경은 허용 파일에만, 기존 기능과 안전 설정을 보존한다.

동작 변경은 실제 연결 지점에서 RED를 확인한 뒤 최소 수정으로 GREEN을 만든다. API/폼/다운로드 등의 통합이 실제로 실패할 수 있는 테스트를 택하고, 과한 모킹으로 연결을 제거하지 않는다. 비동기는 동작 전에 정확한 이벤트/상태 신호를 구독하고 제한 시간 내 기다린다. 시간 자체가 대상이 아니면 고정 sleep·폴링 지연을 쓰지 않는다. Bun 대상은 관련 `bun test`를 한 번의 실행에서 안정적으로 통과시킨다. 시각·카피·문서만 바꾸면 실제 화면 리뷰로 검증하며 문구/프롬프트/문서 원문 고정 테스트를 만들지 않는다.

### 8. 실제 브라우저 전체 검수

오케스트레이터가 실제 실행 명령·URL·빌드 모드·버전을 기록하고 실제 앱을 Aside에서 연다. `design/evidence/<run-id>/manifest.md`에 **전체 섹션 x breakpoint x 해당 상태**를 빠짐없이 연결한다. 모바일·태블릿·데스크톱과 계약의 breakpoint 경계, 좁은 화면, 확대/reflow를 포함한다. 기본·hover·focus·active·메뉴 열림·loading·empty·error·success·disabled는 존재하는 상태만 재현하고 나머지는 이유 있는 N/A로 둔다.

전체 페이지와 가독성 있는 섹션 캡처, 키보드 이동·실제 CTA/파일/폼 동작, 폰트·이미지 실패, reduced motion, 고정바 가림, 콘솔/네트워크 오류를 확인한다. 폰트·이미지 로드와 해당 상태의 정확한 신호 후 캡처한다. 치수·대비·접근성 도구 결과와 픽셀 리뷰를 함께 보존한다. 안전한 환경이 없는 운영 제출은 하지 않고 미검증으로 남긴다. 코드·고정 시안만 확인했으면 실제 반응형 검수 완료가 아니다.

### 9. 시각·카피 교정과 재심

큰 빈 공간 속 작은 본문, 고아 음절, 잘린 얼굴/포커스, 겹친 제품 화면, 색상칩뿐인 디자인 비교, 흐린 캡션, 문의와 떨어진 CTA, 반복·과장 문구를 실제 화면에서 교정한다. 배치가 맞는다는 이유로 상품성 부족을 통과시키지 않는다. 수정본마다 새 컨텍스트의 이미지 리뷰어 두 명이 실제 DOM 캡처의 전 섹션을 독립 채점한다. 이전 세션을 되살려 큰 이미지 문맥과 오래된 판단을 반복하지 않는다. 변경 섹션과 영향받는 이웃·breakpoint·상태를 재캡처하고 양쪽 최종 평가가 모두 루브릭 게이트를 충족해야 한다. 승인된 방향 안에서 고치며 취향 조사부터 다시 시작하지 않는다.

### 10. 정확한 HEAD의 fresh ultrabrain 최종 리뷰

관련 진단·동작 테스트·빌드·실제 화면 검수를 마친 뒤 코드와 자산을 동결한다. 커밋은 명시적인 사용자 권한이 있을 때만 만든다. 미커밋 변경을 현 HEAD의 검수라고 부르지 않는다. 커밋 권한/검수 대상 버전이 없으면 최종 게이트는 대기다.

새 컨텍스트의 **ultrabrain 리뷰어 1명**에게 `git rev-parse HEAD` 결과로 고정한 후보와 diff 범위·계약·실제 화면 증거·검증 로그·제한 사항을 준다. 리뷰 전후 HEAD와 작업 트리/자산 일치 여부를 확인한다. 증거 생성 이후 변경이 있으면 후보에서 재검증·재캡처한다. 리뷰 보고서는 대상 트리 밖의 승인된 증거 저장 위치에 두어 검수 대상 HEAD를 스스로 바꾸지 않게 한다.

리뷰어는 기존 PASS를 답습하지 않고 품질, 동작 연결, 의료/개인정보, SEO 주장, 승인·증거 정합성을 확인한다. 이미지 판독이 불가능하면 그 한계와 두 이미지 리뷰어의 구체적 관찰 출처를 밝힌다. 차단 결함·증거 공백이면 HOLD다. 수정하면 이전 판정은 만료되고 새 후보에 fresh 최종 리뷰를 다시 받아야 한다. 같은 후보의 중복 최종 리뷰단을 만들지는 않는다.

### 11. 인계와 권한 있는 병합

[체크리스트](references/checklist.md)에 완료·실패·미검증·소유자 대기를 구분해 인계한다. **로컬 noindex 빌드 품질**, **소유자 승인 공개 출시**, **관측된 검색/예약 성과**를 따로 보고한다. Lighthouse 점수 때문에 noindex, 인증, 개인정보 동의, 의료광고·환자자료 보호를 제거하지 않는다. noindex는 보안 대체물이 아니다.

공개는 공식 호스트·사업 신원·문의 경로·자료 권리·운영 책임과 별도 출시 승인이 있어야 한다. 그때만 실제 배포와 canonical/robots/sitemap/metadata/schema 정합성을 확인한다. 클릭, 상담 접수, 예약 확정은 서로 다른 사건이며 색인·검색 순위·AI 인용·예약 증가는 측정 전에는 미확인이다.

병합은 별도 명시 권한, 최종 리뷰 대상 HEAD와 현재 후보 일치, 미해결 차단 결함 없음이 모두 확인될 때만 한다. 대상 브랜치 통합으로 코드가 달라지면 바뀐 결과를 재검증한다. 공개·병합 대기 상태는 로컬 작업 실패도 공개 완료도 아니다.
